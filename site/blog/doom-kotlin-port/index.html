Porting DOOM means
preserving its decisions.

Fixed-point maths, independent worlds, and the boundary between a 35 Hz engine and Compose.

A game engine port has a demanding definition of correctness. A familiar-looking frame is useful, but it cannot tell you whether movement, collision, random choices, and simulation order still agree. In this Kotlin DOOM project, the interesting engineering lives between two goals: retaining the translated engine’s behaviour and giving a modern application clear ownership of its resources.

This walkthrough follows the source at commit cbcdaa0. It focuses on the contracts that make those goals compatible, rather than treating a successful launch as proof that the whole port is correct.

Arithmetic is part of the contract

The engine represents fixed-point values as Kotlin Ints, with 16 fractional bits. Multiplication promotes both operands to Long, multiplies them, shifts the result right by 16, and converts back to Int. Division has an explicit overflow guard before its widened integer calculation. These choices are visible in the fixed-point implementation.

The important property is the sequence of operations. Replacing that sequence with floating-point arithmetic can change rounding; a small numeric change can become a different branch in later simulation. “Cleaner” arithmetic therefore needs a behavioural argument, not just an equivalent-looking formula.

The translation conventions make the same distinction for angles, signed shifts, and buffer offsets. They preserve compatibility-sensitive decisions while allowing the application around the engine to change. A port is easier to reason about when arithmetic changes and ownership changes are reviewed as separate concerns.

Two clocks, different jobs

The application’s display callback and the game’s simulation clock have different responsibilities. RunGameSession waits for a frame opportunity and calls the engine’s step function. Inside the engine, TryRunTics advances simulation according to the engine clock’s 35 Hz timing. One display callback is not a promise of exactly one simulation tick.

This is a simplified path through the actual session and adapter boundaries:

FrameClock.awaitFrame()
  → DoomEngineAdapter.step()
  → DoomEngine.step()
  → D_DoomStep(): advance simulation, render
  → DoomVideo.present(borrowed pixels)
  → GameFrame(copied pixels)
  → presentation state

The engine facade also accepts a clock through its host contract. Tests can supply controlled time; the application can use monotonic elapsed time. Separating those jobs makes repeatable stepping possible without making the browser’s refresh rate part of game logic.

A frame needs an owner

The video callback receives a borrowed pixel buffer. Holding that array directly would let later rendering alter an earlier “frame” while the UI still references it. The adapter solves this at the boundary: it wraps the output in a GameFrame, which checks the dimensions and copies the pixels.

Copying is a concrete cost, but it purchases a concrete guarantee: future engine writes cannot change the published snapshot. The array remains mutable to its consumer; this is ownership isolation, not language-enforced immutability.

That distinction generalizes to camera previews, audio visualizers, and streaming charts. Before optimizing away a copy, establish who may reuse the buffer, who retains it, and when that retention ends. A fast buffer with an unclear lifetime can produce failures that look like rendering bugs.

One engine, one world

Each DoomEngine creates a DoomEngineCore with its own simulation, renderer, resource, input, and random state. This gives a restarted game a fresh runtime instead of relying on every old mutable value being reset correctly.

Lifecycle suspension has a different meaning. The adapter detaches the engine, releases audio, and later resumes the same instance. A terminal failure or quit needs a new session. Those are separate transitions, even if both briefly show the same application screen.

Ownership does not eliminate all coupling. Compatibility functions still use a broad core receiver to reach other subsystems. The useful achievement here is explicit lifetime and independent state; narrower internal interfaces remain another step. Keeping those claims separate makes an architecture review more precise.

What demo checkpoints prove

The demo harness advances a controlled clock, disables drawing, and records simulation checkpoints every 35 ticks and at completion. It hashes player state, actors, sectors, and the random-sequence position in a fixed order. Comparing simulation state avoids making screenshot differences the only signal.

The regression tests expect three recorded demos to finish at their established tick counts with their established hashes. This is characterization testing: it checks that the refactored port retains the earlier port’s behaviour for those recorded paths.

The baseline matters as much as the assertion. Matching a previous Kotlin implementation is evidence against a refactor regression. It is not independent proof of parity with the original DOS executable.

Keep the boundaries visible

The launcher accepts locally supplied original game data and remembers it on the device. Retail assets are not included. At this source snapshot, the project’s verification record explicitly leaves full retail gameplay unverified; malformed map/save/demo recovery and physical-device behaviour also need further work. A build target or a passing demo cannot settle those questions.

The broader engineering lesson is to make preservation measurable. Keep numeric behaviour explicit, isolate mutable lifetimes, and choose fixtures that can detect drift. Then improve the host application around those boundaries, with a clear account of what each test actually establishes.
