A sorted array tells you where an algorithm ended. It leaves out the decisions that got it there. An algorithm visualizer has a different job: preserve enough of those decisions that someone can stop, move backward, and understand the transition.

AlgoScope approaches that problem with Dart step generators and a shared Flutter player. Its useful architectural idea is the boundary between calculating a run and displaying it. This walkthrough follows the September 9 source snapshot. The examples below are traced from that code.

Frames before animation

The central array model, ArrayFrame, stores values alongside sets of indices: which elements are being compared, which are active, and which are finished. It also has optional search bounds, a pivot, a target, and a caption. An array alone cannot distinguish “examining these values” from “these values are settled.” These fields make that distinction explicit. See the frame model.

The model is annotated @immutable, but its collection fields are still ordinary Dart lists and sets. The annotation does not freeze their contents. Snapshot correctness therefore depends on ownership: generators must copy mutable working data when recording a frame, then leave the recorded collections alone. That is a useful distinction when reviewing any replay system. A final field prevents replacing a reference; it does not prevent changing the referenced list.

One player, many algorithms

VizRun exposes a frame count, a function that returns the caption at an index, and a builder that renders that index. It can also supply a legend. The player does not need to know whether the underlying algorithm manipulates arrays, graphs, or boards. Its contract is simply “show step i.” See the run contract.

The catalog’s array adapter connects a list of frames to BarsView and forwards each frame’s caption. See the adapter. Playback then advances an integer on a timer. Manual stepping pauses that timer; restarting returns to index zero; requesting new input creates another run. Keyboard controls include stepping with the arrow keys and jumping to either end. Crucially, going backward does not require writing an inverse sorting operation. See the player controls.

A three-number walkthrough

Consider passing [3, 1, 2] to the bubble-sort generator. Reading its nested loops gives this seven-frame trace. The descriptions are abbreviated here; “finished” refers to zero-based indices.

1  [3, 1, 2]  Initial values
2  [3, 1, 2]  Compare indices 0 and 1
3  [1, 3, 2]  Swap indices 0 and 1
4  [1, 3, 2]  Compare indices 1 and 2
5  [1, 2, 3]  Swap indices 1 and 2
6  [1, 2, 3]  Compare 0 and 1; index 2 finished
7  [1, 2, 3]  All indices finished

The array is ordered at frame five, but the algorithm still performs its next comparison. That distinction is the lesson: a visual state and an algorithm’s termination condition are different things. Comparisons receive their own snapshots, including comparisons that cause no swap. The generator copies both values and the accumulated finished set when recording those states. Follow the complete generator.

Drawing what the state means

BarsView translates those roles into colors with an explicit priority: finished, active, comparing, pivot, then search-window emphasis. If roles overlap, the order determines what the reader sees. That makes rendering precedence part of the explanation, rather than an incidental styling decision.

The painter also handles negative values around a zero baseline instead of treating every bar as a positive height. Before painting, the widget measures value labels and uses them to choose a minimum canvas width inside a zoomable container. These details matter because a visualizer must preserve the meaning of its input as the numbers or available space change. Read the bar renderer.

Test the intermediate story

A final-answer test is necessary but incomplete. AlgoScope’s sorting tests compare the last frame with Dart’s sorted result and check highlight indices along the way. See the sorting checks. A separate integrity suite inspects every catalog frame, verifies caption agreement, and fingerprints its data. It creates another run, revisits the old run backward, and checks that those fingerprints remain unchanged. See the replay checks.

Rendering tests visit every generated frame at phone and desktop canvas sizes in both themes. Full-player tests additionally seek to the beginning, middle, end, and longest caption under several viewport and text-scale combinations. These tests check for exceptions and expected text; they do not establish pixel-perfect design or correctness for every possible input. They do, however, ask a better question than whether the opening screen renders. See the rendering coverage.

The cost of keeping every step

Saved frames make random access simple, but they consume memory. The bubble-sort implementation keeps a full array copy for each recorded comparison and swap, so the visualizer has a different storage cost from an in-place sort. AlgoScope’s documentation explicitly separates algorithm complexity from saved animation frames. Read the complexity note.

For larger inputs, a possible next design would store events or periodic checkpoints and reconstruct intermediate states. That would trade memory for more replay logic; it is an alternative, not a capability claimed here. For small teaching examples, explicit snapshots keep the implementation easy to inspect.

The reusable idea: define what one meaningful step contains before deciding how it moves. Once the state explains the algorithm, playback and rendering can remain separate concerns.
