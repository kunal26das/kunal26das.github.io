Before an application draws its first useful screen, several components may need to exist. Analytics might need a logger. A client might need configuration. As that list grows, an ordering requirement can disappear inside an entry point that looks like ordinary setup code. Moving a line can then change behavior without changing any component's declared contract.

Startup makes those relationships explicit in Kotlin Multiplatform. Its shared initializer API connects to AndroidX on Android; other targets use the project's own runtime. This walkthrough follows the source snapshot linked below and focuses on how the graph is described, checked, and executed.

Declare what must exist first

An Initializer<T> has two jobs: describe prerequisite initializer keys through dependencies(), then build a value through create(context). The value can be a service, or Unit when initialization only performs work. This separates a component's ordering contract from the code that starts it. The shared interface is small enough to read in one sitting.

The README's logger and analytics example illustrates the distinction. Analytics declares the logger as a dependency and retrieves it inside create. The arrow below means “must finish before,” so it points from the prerequisite toward its consumer. It represents that example, rather than an additional library API.

LoggerInitializer  ── must finish before ──▶  AnalyticsInitializer
   registered lazy                              registered eager

Startup order: Logger → Analytics

Declaring the edge keeps the requirement visible wherever the initializer is installed. Registering analytics first in a manifest does not remove its prerequisite. The complete quick start supplies the classes, imports, registrations, and host entry point.

Follow the eager roots

A StartupManifest registers factories under initializer keys. metaData marks eager roots; lazyInitializer makes a component available when requested. A lazy registration can still run during launch: in the example, the eager analytics component reaches the logger through its dependency. To understand launch work, follow every eager root's dependencies.

Manifests also compose. A later registration can replace an earlier one, and a removal can hide a registration. The manifest implementation checks that a factory produces the exact initializer class named by its key. That prevents one registration from describing different components on different platforms.

There is a separate lifetime question. The non-Android engine caches completed products by key and passes those keys into later planning as already satisfied. Installing another manifest merges registrations, while an existing product remains cached. An override therefore changes a registration; it is not a mechanism for replacing a running service. This behavior is visible in StartupEngine.

Inspect the plan before execution

StartupPlanner first collects the dependencies reachable from the requested roots. It counts each component's unmet prerequisites, then repeatedly takes the ready components and reduces those counts for their dependents. This is Kahn's algorithm, implemented iteratively. The resulting order places dependencies before consumers; waves groups components whose dependencies belong to earlier groups. Already satisfied keys are excluded from the pending work. See the planner implementation.

A useful distinction is which roots get checked. Planning eager roots checks their reachable graph. StartupPlanner.validate(manifest) instead starts from every registered component, including lazy ones. A broken feature should be discoverable before a user is the first person to request it.

The planner tests cover this with an entirely lazy cycle, alongside diamond dependencies, duplicate edges, and partially satisfied graphs. They assert both ordering and the component keys reported for failures. Those cases describe useful application-level tests too: shared prerequisites should appear once, and a cycle should identify the relationship that needs changing.

Planning does not call create, but it does construct initializers and read dependencies(). Keep factories and dependency declarations free of service-starting side effects so validation remains useful.

Keep the Android boundary visible

On Android, the project's Initializer is a type alias for AndroidX's interface. AndroidX constructs initializer classes reflectively. The shared Kotlin factories are ignored during Android installation, so an initializer needs a public no-argument constructor. Platform resources and dependencies belong in create.

Automatic startup still needs Android manifest metadata. The Kotlin manifest does not generate that XML. An eager root can work elsewhere yet never start automatically on Android if the corresponding metadata is absent. The project's Android guide includes a parity-test approach for the registrations an application owns.

Manual startup is available too: Android's Startup.install asks AndroidX to initialize the Kotlin manifest's eager roots. Its runner overload delegates to the same path. These details in the Android bridge explain why sharing declarations still requires explicit host integration.

Choose execution deliberately

The default runtime executes sequentially on the calling thread. A wave identifies declared independence, but thread requirements remain a separate concern. For custom runners, the documented contract requires invoking each task once and waiting for completion. During installation, tasks that read through AppInitializer must stay on the installing thread, even when reading a dependency from an earlier wave.

Likewise, CoroutineInitializer is a blocking bridge around suspending work; it does not turn installation into a suspending API. The bridge is unsupported on JavaScript and Wasm. The runtime guide explains these execution constraints. Start by making the graph correct and keeping launch work small. A clear dependency model makes later scheduling decisions easier to inspect.
